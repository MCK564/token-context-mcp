# Hybrid & Batch Orchestration Recipes (Path B / M2)

This guide covers semi-automatic and hybrid workflows where a deterministic rules table guides subtask allocation, orchestrating parallel worker fan-outs and multi-stage dependency DAGs with strict barrier joins and budget controls.

---

## Recipe R03: Independent Batch Fan-Out

### 1. When to Use
- You have multiple non-overlapping files or components to analyze, document, or test simultaneously.
- Subtasks share no state and can execute concurrently without race conditions.
- **Anti-pattern**: Launching unbounded parallel workers (e.g. 10+ concurrent agents) that exhaust rate limits, blow past budget caps, or overload the supervisor's synthesis context.

### 2. Prerequisites
- Host or orchestrator supporting asynchronous or background subagents (`max_parallel_workers=2` recommended for pilot).
- Pre-allocated budget reserves in the authoritative ledger for each worker attempt.
- Explicit `TaskSpec` per batch item with non-overlapping file scopes.

### 3. Inputs & Outputs
- **Input**: A list of independent target files (e.g. `[src/.../sqlite_store.py, src/.../runner.py]`).
- **Output**: An ordered collection of `WorkerResult` records joined strictly by `task_id` upon completion.

### 4. Step-by-Step Procedure
1. **Rule Evaluation**: Check rule table; confirm all tasks match `extract_evidence` or `summarize_source` with clear file ownership.
2. **Budget Reservation**: Reserve `estimated_cost * 1.2` for each batch worker in the ledger.
3. **Bounded Fan-Out**: Dispatch at most `max_parallel_workers` concurrently using isolated context packets.
4. **Barrier Synchronization (Join)**: Await completion of all dispatched tasks. If one worker fails or times out, record `status="failed"` or `status="partial"` without dropping completed peer results.
5. **Deduplication & Assembly**: Sort results deterministically by `task_id` and deliver compact summaries to the supervisor.

### 5. Concrete Execution Trace (Labeled Illustrative)

```text
[ORCHESTRATOR]: Initiating batch analysis for 2 files: sqlite_store.py, runner.py.
[BUDGET LEDGER]: Reserving $0.0050 per worker. Total reserved: $0.0100. Status: OK.
[DISPATCH]:
  - Worker 1 -> TaskSpec(task_id="batch_01", file="sqlite_store.py", model="MODEL_ECONOMY")
  - Worker 2 -> TaskSpec(task_id="batch_02", file="runner.py", model="MODEL_ECONOMY")
[EVENT]: Worker 1 completed in 2.1s (Status: completed, Tokens: 1,120)
[EVENT]: Worker 2 completed in 2.8s (Status: completed, Tokens: 1,340)
[JOIN BARRIER]: Both task_ids accounted for: ["batch_01", "batch_02"].
[VALIDATION]: Mechanical schema and hash validation passed for both results.
[SETTLEMENT]: Actual cost settled in ledger: $0.00038. Unused reservation released.
[SUPERVISOR]: Receives joined results; synthesizes cross-file analysis.
```

### 6. Result Verification
- Confirm that the join barrier received results matching the exact set of dispatched `task_id`s.
- Verify that total concurrent workers never exceeded `max_parallel_workers=2`.
- Check ledger reconciliation: active reservations returned to 0 after settlement.

### 7. Cost & Risk Profile
- **Latency Advantage**: Wall-clock time reduced by ~40% compared to sequential execution.
- **Token Overhead**: Parallel coordination incurs slight ledger tracking overhead, but context isolation prevents quadratic history inflation.

## Recipe R04: Dependent Task DAG Execution

### 1. When to Use
- Subtask B strictly depends on the accepted output or artifact generated by Subtask A (e.g. generate interface contract first, then implement unit test).
- **Anti-pattern**: Discarding dependencies and running dependent tasks prematurely on stale or unvalidated inputs.

### 2. Prerequisites
- Graph controller or orchestrator capable of tracking task state transitions (`pending`, `ready`, `running`, `accepted`, `failed`, `blocked`).
- Acyclic dependency graph verification prior to scheduling.

### 3. Inputs & Outputs
- **Input**: A dependency specification: `Task A (root)` -> `Task B (depends on A)`.
- **Output**: Accepted terminal results for both tasks or early termination with an explicit blocked reason if Task A fails.

### 4. Step-by-Step Procedure
1. **DAG Pre-validation**: Verify the dependency graph has no cycles, duplicate IDs, or missing dependency targets.
2. **Execution of Prerequisite (Task A)**: Mark Task A `ready` and dispatch to worker or tool. Task B remains in `pending` state.
3. **Verification of Task A**: Task A completes. Validator checks acceptance criteria.
   - *If Rejected/Failed*: Mark Task A `failed`. Transition Task B immediately to `blocked` (terminal). Abort downstream calls to protect budget.
   - *If Accepted*: Mark Task A `accepted`. Earmark Task A's output artifact handle as context for Task B.
4. **Transition & Dispatch of Task B**: Mark Task B `ready` and dispatch with Task A's verified evidence reference.
5. **Final Join**: When all tasks reach a terminal state, notify supervisor for final answer compilation.

### 5. Concrete Execution Trace (Labeled Illustrative)

```text
[DAG SCHEDULER]: Registered DAG:
  - Task A: "Extract public API signatures from server.py" (dependencies: [])
  - Task B: "Draft test cases matching API signatures" (dependencies: ["Task A"])
[CYCLE CHECK]: Acyclic graph verified. Zero cycles detected.
[STEP 1]: Dispatching Task A to MODEL_ECONOMY. Task B is PENDING.
[STEP 2]: Task A returns WorkerResult with 9 signatures and verified line hashes.
[STEP 3]: Validator accepts Task A -> State: ACCEPTED.
[STEP 4]: Dependency satisfied for Task B. Transitioning Task B to READY.
[STEP 5]: Dispatching Task B with context: ArtifactRef(Task A, revision=1).
[STEP 6]: Task B returns test cases -> State: ACCEPTED.
[SYNTHESIS]: Supervisor reviews accepted test suite and delivers final plan.
```

### 6. Result Verification
- Check state history: Task B was never dispatched before Task A reached `accepted`.
- Negative validation drill: If Task A is artificially failed, Task B must transition to `blocked` without consuming LLM tokens.

### 7. Cost & Risk Profile
- **Savings Guard**: Prevents wasting tokens on downstream tasks when upstream dependencies fail.
- **Overhead**: Minimal graph state accounting (~0.01s scheduler overhead).
